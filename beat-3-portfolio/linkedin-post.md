Built evaluation tools to guide myself through open source contribution: selecting issues, reproducing bugs, planning fixes, and reviewing pull requests. I opened a real PR that fixed a test indentation issue in a live repository.

Based on the project, I have learned that criteria needs clear definitions. Words like 'professional' or 'focused' can have varied meanings based on context. Consequently, when I replaced vague language with observable facts ("changes are exactly those in the plan" instead of "stays focused"), my evaluation criteria achieved perfect agreement across all review categories.

This skill transfers directly to code review checklists, test cases, and how I communicate about work on any team.
